# ADR-12：Node.js 支持矩阵（放弃 18/20，支持 22+）

- 状态：**已采纳**（v0.14.1）
- 影响面：`package.json`（`engines`）、`README.md`、`docs/quality/*`、
  `test/unit/test-node18-esm-plugin-shape.test.mjs`、`.github/workflows/*`
- 决策者：**维护者（用户）**。原话（2026-10-23）："咱们不追求 node18 适配啦。放弃这个平台。
  22以上OK就行了。"
- 触发：专家 0.14.0 复审 §5 指出执行方准备把"Node 18/20 实测"列为冻结前置条件，
  而这两条线都已结束官方维护；建议二选一（方案 A：正式支持 22+，方案 B：继续承诺 18/20
  但必须分别全链路实测）

## 1. 决定

**正式支持：Node.js ≥ 22.0.0。** Node 18 与 Node 20 不再支持，不再测试，不再为它们做兼容。

- `package.json` 的 `engines.node` 从 `>=18.0.0` 改为 **`>=22.0.0`**。
  npm 会在不满足时给出警告（未开 `engine-strict` 时不是硬失败，这是有意的：
  让用户在旧版本上仍能**装上并看到明确的运行时诊断**，而不是装不上却不知道为什么）。
- 说"支持 22+"，**不等于说"22 与 24 都实测过"**。见 §4。

## 2. 为什么这个决定是对的（不只是"省事"）

专家 §5 的方案 A 与方案 B 都成立，选 A 的理由：

1. **18/20 已 EOL**（18 于 2025-04 结束，20 于 2026-04 结束）。继续承诺它们，
   等于承诺为一个不再收到安全修复的运行时提供支持——这不是稳妥，是负债转移给用户。
2. **本项目的 Node 版本敏感性是真实的**，不是理论风险。v0.10.1 记录过一个**真阳性**：
   Node 18 不做 ESM 语法探测，于是用户插件目录缺 `package.json` 时，
   同一份插件在 22 能装、在 18 报 `Unexpected token 'export'`。
   既然差异真实存在，**每一版都必须在每条承诺的版本上实跑**——
   而每多承诺一条线，就要多一套全链路。"承诺但不测"是最坏的一档。
3. **兼容层没有收益。** 为 Node 18 保住 ESM 探测那一段，需要一个语法预扫描或
   强制改名，两者都会把"用户写错了"与"运行时版本差异"搅在一起。

## 3. Node 18/20 上的已知事实（不隐瞒，也不再维护）

放弃支持**不等于**"在 18/20 上什么问题都没有"。已查实的两件事，记录在此：

1. **v0.10.1 的 ESM 形态真阳性**：见 §2.2。产品行为是对的（换成具名
   `plugin_module_not_esm` + 可执行建议），这条代码**保留**，因为它在 22 上
   对"用户在 CommonJS 包目录里写 export"仍然是有用的诊断。
2. **`test/unit/test-node18-esm-plugin-shape.test.mjs` 的 N18/c 在 Node 18 上是红的**，
   而这不是产品缺陷：该用例直接调 `pm._importPluginModule`，却没有像真实宿主
   （`src/bootstrap/cli.js`、`scripts/cli.mjs`）那样注入 `core.esmHint`；
   而 K-14/2 明确约定"宿主未注入 ⇒ 退化为原始错误，不静默丢失"。
   也就是说**是测试漏了一步，产品行为正确**。

   这件事值得单独记一笔，因为它是"NOT_RUN 掩盖了错误判据"的标本：
   v0.13.0 与 v0.14.0 都把 Node 18 标成 NOT_RUN，于是这条错误的用例两版都没被发现。
   **本条不修**（那要在已放弃的平台上修），但保留文件与其历史注释，
   把真实成因写在测试文件头，避免下一个人以为"18 上一片红说明质量差"。

## 4. 支持矩阵（"支持"与"实测"分开写）

| 版本 | 支持状态 | 本轮实测 | 说明 |
|---|---|---|---|
| **22.x** | **正式支持** | ✅ 全量（开发树单测 1020 / 1008 通过 / 12 跳过；**制品净室解包** 1020 / 1006 通过 / 14 跳过；集成 56/56；smoke 2/2；12 套探针 rc=0） | 本轮唯一实跑线（实测 22.22.2） |
| **24.x** | **正式支持** | ✅ **已实跑**（v24.9.0，单测 1302/1302，2026-10-27） | 原为 NOT_RUN；rc.19 补测后转绿，见 §4.1 |
| 20.x | 不支持 | — | EOL |
| 18.x | 不支持 | — | EOL；历史真阳性见 §3.1 |

**"正式支持但未实测"这一格必须显式存在，不能靠读者自己推断。**
专家 §1 的做法（把 NOT_RUN 与 PASS 分列）是对的，本 ADR 沿用。

### 4.1 对 Node 24 的处理（诚实说明）

> **rc.19 更新（2026-10-27）：本节结论已被实测取代，原文保留在下方，不抹掉决策历史。**
>
> 装上 Node **v24.9.0** 后跑全量单测，**首轮 1301/1302 —— 抓到一个真失败**。
> 根因：`test/unit/test-r0-125-g0-durable-workspace-and-fence.test.mjs` 用 `rmSync`
> 删符号链接，而 **Node 24 起 `rmSync` 对符号链接抛 `ERR_FS_EISDIR`**（Node 22 不抛）。
> 产品代码删链接走 `unlink`，所以这是**夹具写法问题，不是产品缺陷**；改成 `unlinkSync`
> 后两个大版本都是 1302/1302。
>
> 这恰好说明：**"声明支持但不实测"会把真实差异藏起来**。这条夹具缺陷在只跑 22 的
> 世界里永远不会露头。同时它也印证了 §4.2 第 1 条（不宣称未验证的东西已验证）是对的 ——
> 如果我们当时写了"24 应该没问题"，这个缺陷就会被一句漂亮话盖过去。
>
> 因此发布门禁把 `node-24` 从 `NOT_RUN` 改成**实跑项**：`release-gate.mjs` 的
> `findOtherNodeMajor()` 找到其它大版本就真跑整套单测（找不到才记 NOT_RUN 并写明找过哪里）。
> 注意这里修掉了一个**门禁自身的洞**：原写法是 `if (major !== 24) notRun(...)`，
> 只在"跑不了"时记账 —— 于是本机真有 24 时，这一项会**从清单里消失**，PASS 不加、
> 总数还变少，等于"跑成了反而不如没跑"。
>
> **仍未做的：CI 双版本矩阵**（§5 第 3 条仍然成立）。本机实测替代不了矩阵。

<details>
<summary>以下为 rc.19 之前的原文（已过时，保留以备对账）</summary>

本机只装了 18.20.8 / 20.20.2 / 22.22.2，**没有 24**。三条路：

- 装 24 实跑 → 最干净，但本轮不做（不为了一个格子引入新运行时，且 24 尚未成为
  主要部署目标）。
- 只声明支持 22 → 最保守，但 `engines: ">=22"` 的语义本来就不排斥 24，
  硬写成 `>=22 <24` 会传递"24 有问题"的错误信号。
- **声明 22+ 并把 24 标 NOT_RUN** → 采用这条。风险由 §4.2 的机制兜住。

</details>

### 4.2 兜住"未实测的 24"的三道措施

> **rc.19 更新**：标题里的前提已不成立（24 已实测，见 §4.1）。以下三道措施**仍然保留**，
> 因为它们的价值不在于"24 没测"，而在于"**任何未实测的版本都不得被背书**"。
> 逐条改注如下。

1. ~~**不宣称 24 已验证**：README、发布判定、本 ADR 一律写"22 实测 / 24 NOT_RUN"。~~
   → 现改为：**README、发布判定、本 ADR 只写实测到的那两个版本**（22.22.2 与 24.9.0），
   其它版本仍一律不背书。规则本身没变，变的是已实测集合从 1 个变成 2 个。
2. **不新增新版本的特性依赖**：`test/unit` 里已有守门用例
   （`N18/f`：随包代码不得使用 Node 20.11+ 才有的 `import.meta.dirname/filename`）。
   这条从"为 18 兼容"转为"**为未实测版本留安全边际**"——依赖面越小，跨版本漂移越少。
3. **`engines` 与实测的差异可被外部复核**：任何拿到包的人跑
   `node --version` + `node test/run-all.mjs` 就能自己验证某个版本是否可用。
   我们只承诺自己实测过的，不做无证据的背书。

## 5. 本决定**不**解决的问题

- **不再有"跨大版本兼容"的证据链。** v0.10.1 那套"在 18 上抓到的真阳性"证明
  多版本实测有价值。放弃 18/20 之后，这条证据链只剩单一版本——
  这是本决定的**代价**，不是零成本。
  **rc.19 部分补回**：新增 24.9.0 实测（并因此抓到 1 个 Node 24 专属的夹具缺陷，
  见 §4.1）。证据链从 1 个版本变成 2 个，但**仍不是矩阵**。
- **冻结判定中"Node 18/20 未复验"这一条，从"欠账"变为"不再适用"**，
  **不是**"已完成"。发布判定文档必须这样记：它被**撤销**，不是因为被满足。
- **CI 矩阵仍未真正建立。** 本轮是把 `engines` 与文档对齐，不是搭好了
  Node 22/24 的双版本 CI。若将来要恢复跨版本承诺，先建矩阵，再改 `engines`。
  当前 `release-gate.mjs` 里的 `node-24` 项是**本机实跑**，不是 CI 矩阵；
  换一台没有 24 的机器跑，它会如实退回 `NOT_RUN`。
