# 土行孙压测基线（2026-10-20 · v0.9.15）

> 这是**第一份**基线。此前仓库里只有压测入口、没有压测资产，所以"性能如何"没有任何数字。
> 本表之后每轮都应重测并追加一列；比对新旧两列之前，**先确认硬件是同一档**。

同一台机器上，延迟/吞吐这一类数字的运行间波动约 **±5–10%**（本版两次全量跑的对比：
网关吞吐 14.1k → 13.8k req/s，启动 117 → 122 ms）。所以记录型指标的门槛定在 2×，
而不是 10% —— 把噪声当回归，最后没人看红。

## 结论先行

- **一次完整对话往返中，土行孙内核只占 1–5 毫秒**（L5，mock 上游可控延迟）。用户感受到的"慢"来自上游，不来自本仓。
- **工具路径的安全判据单次 7 微秒**，跑在每次工具调用的必经路径上，代价可以忽略。
- **判据复杂度是线性的**：10 组对抗形态从 5k 放大到 60k，最坏放大比 16.4×（线性 ≈ 12×，二次会是 144×）。
- **没有泄漏**：120 秒 / 8750 万次操作，GC 后活对象漂移 0.0%，监听器漂移 0。

## L1 内核原语

| 操作 | 单次 | 备注 |
|---|---:|---|
| `getService` 命中 | 20 ns | 未命中 17 ns（同样是 Map 访问） |
| `emitFast`（10 监听器） | 135 ns | 纯 EventEmitter 路径 |
| `emit`（10 监听器） | 979 ns | 含 `Object.freeze({...payload})` + `toISOString()`，是 `emitFast` 的 **7.1×** |
| `callCapability` | 1.25 µs | 扣掉 `await` 底噪 104 ns 后净开销 **1.15 µs** |
| 监听器注册 2000 次后按 owner 注销 | 残留 **0** | `MaxListeners` 警告 0 次 |

`emit` 的 7 倍代价是有意的设计（事件不可变 + 时间戳统一）。这组数字存在的意义是：将来若要动它，先有据可依。

## L2 工具路径（每次工具调用的必经路径）

| 场景 | 数值 |
|---|---:|
| 危险判定两层合计（良性命令） | 7.17 µs |
| 危险判定两层合计（危险命令） | 6.18 µs |
| 软闸 `check()` 良性路径 | 2.12 µs |
| 软闸计数 1 万文件目录 | 9.0 ms（扫描上限 2000 条，如实报 `unbounded`） |
| 执行器全链路 `tool-read` | 2.36 µs |
| 执行器全链路（硬拦命中） | 3.85 µs |
| ReDoS 最坏放大比（5k→60k，10 组形态） | **16.38×**（线性 ≈ 12×） |
| ReDoS 最坏单次（6 万字符输入） | 16.5 ms |
| 危险语料漏判（312 条） | **0** |
| 良性语料误判（280 条） | **0** |
| 高负载 59,200 次混合后判定漂移 | **0** |
| 8 会话交错锁定 / 新会话不继承拒绝 | 通过 |

语料构成：39 条危险基座 × 7 种换壳（sudo / timeout / env / `&&` / `;` / `||` / `bash -c`）= 312 条；44 条良性基座 × 5 种良性壳 + 16 条"危险串在数据位置"= 280 条。另有 7 条射程外、6 条有意保守拦截，单独报告、不判失败（清单见 `test/stress/lib/corpus.mjs`）。

## L3 上下文与会话

| 场景 | 数值 |
|---|---:|
| `trimMessages` 100 条 | 0.03 ms |
| 1,000 条 | 0.11 ms |
| 5,000 条 | 0.31 ms |
| 10,000 条 | 0.58 ms（保留 144 条） |
| 预算为 0 的退化路径 | 不抛异常，退到最小集 |
| 单条消息 1 MiB | 不崩，0.63 ms |
| 单会话追加写 1000 次 | 63.7 ms |
| 读回 1000 条（页缓存已热） | 微秒级 |
| 32 会话 × 100 次并行追加 | 0 错误 / 0 串话，174.6 ms |

规模行为是线性的：消息数 ×10（100→1000）耗时约 ×3.7，再 ×5（1000→5000）约 ×2.8，符合"每轮只遍历一次"的实现。

## L4 网关

| 并发 | 吞吐 | p95 |
|---:|---:|---:|
| 1 | 4,025 req/s | 0.42 ms |
| 8 | 10,268 req/s | 1.55 ms |
| 32 | 13,787 req/s | 3.34 ms |
| 128 | 10,711 req/s | 30.76 ms |

| 健壮性场景 | 结果 |
|---|---|
| 500 并发连接突刺 | 成功率 **100%**，进程存活 |
| 64 并发 × 4000 请求（keep-alive） | 错误 **0**，p99 12.1 ms |
| 11 MiB 请求体（上限 10 MiB） | 回 **413**，之后健康检查仍 200 |
| 伪造 Origin 访问控制面 | 回 **403** |
| 30 秒稳态（44 万请求） | RSS 漂移 16.1% |

吞吐在并发 32 处见顶（约 13.8k req/s），128 并发时因排队 p95 升到 31 ms。这是单进程单线程的典型形状，不是缺陷。

## L5 端到端（本地 mock 上游，可归因）

| 上游延迟 | e2e p50 | 直连上游 p50 | 内核开销 |
|---:|---:|---:|---:|
| 0 ms | 4.57 ms | 3.23 ms | **1.34 ms** |
| 50 ms | 55.77 ms | 52.77 ms | **3.00 ms** |
| 200 ms | 207.03 ms | 202.12 ms | **4.91 ms** |

上游延迟可加性：设 200 ms，实测差值 202.5 ms，**偏离 2.5 ms**。3 并发会话全部成功。

**读法**：把总耗时减去"直连上游"的耗时，剩下的 1–5 毫秒就是本仓在一次完整对话往返里的全部贡献。这个数字随上游延迟几乎不变，说明内核里没有与上游耦合的等待。

真实免费模型（LongCat 免费档）需要 `.env` 里的凭据，`--live` 才会跑；本轮**未跑**，因此表里没有它的数字。它的绝对值受网络与厂商排队支配，只作趋势参考，不作容量依据。

## G 稳定性（120 秒）

| 指标 | 结果 |
|---|---|
| 总操作数 | 8,750 万次（事件 + 判定 + 软闸 + 文件计数） |
| GC 后活对象漂移（后 60s vs 前 60s） | **0.0%** |
| RSS 漂移（含 V8 保留页） | 2.2% |
| 监听器数量漂移 | **0** |
| 软闸 `_pending` 表大小 | 恒定 **4** 条 |

**口径说明**：泄漏判据用 GC 后的 `heapUsed`，不用 RSS。V8 回收后不把页还给 OS，于是"一次正常的堆扩张"会被 RSS 读成"涨了 19%"——那不是泄漏，是指标在说谎。换成活对象量后是 0.0%，两处数字都保留在报告里，可自行核对。

## 怎么复现

```bash
npm run test:stress                 # 全量，约 3 分钟
npm run test:stress -- --quick      # 跳过 soak 与大目录，约 30 秒
npm run test:stress -- --only=L2    # 只跑某一层
npm run test:stress -- --only=L5 --live   # 含真实免费模型（需 .env）
```
