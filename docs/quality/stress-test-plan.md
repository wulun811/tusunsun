# 土行孙压力测试方案（v1）

> 适用范围：`tusunsun` 0.9.x 开发树与发布产物
> 资产位置：`test/stress/`（**不随发布包分发**，见 §9）
> 入口：`npm run test:stress`

---

## 0. 一句话

**分层压测**：把「我们自己写的代码」和「第三方免费模型」分开计时。前者出可复现的门禁数字，后者只出趋势参考。

不这么做的后果很具体：拿 `longcat-2.5-preview-free` 跑端到端，测出来「一次对话 12 秒」，这个数字里土行孙的贡献是**毫秒级**，剩下的全是网络往返、服务商排队和逐字生成。用它当"性能数据"，等于拿秒表量别人家的服务器。

---

## 1. 为什么必须分层

一次真实请求的耗时可以拆成：

```
用户 → [土行孙网关] → [土行孙内核/工具链] → [上游模型 API] → 逐 token 回传 → [土行孙] → 用户
         └── L4 ──┘   └──── L1/L2/L3 ────┘   └────── 不归我们 ──────┘
```

- **上游不归我们**：免费档还有 QPS/并发额度限制。压它，先撞的是厂商的限流器，不是土行孙的瓶颈。把这个数字当"土行孙的吞吐"是错的。
- **归我们的部分必须可复现**：同一台机器、同样的输入、同样的次数，数字应当稳定在个位数百分比内。做不到，说明测量方法本身有问题（没预热、GC 抖动、后台干扰）。

所以本方案分两层：**受控层**（L0–L4，本机离线，可复现，设门禁）与**参考层**（L5，真实免费模型，只记录，不设 SLO）。

---

## 2. 分层与测量点

| 层 | 被测对象 | 关键指标 | 门禁类型 |
|---|---|---|---|
| **L0 冷启动** | `tusunsun.mjs` 进程起到 `/ready` 200 | `t_ready` p50/p95、峰值 RSS、模块装载数 | 记录 |
| **L1 内核原语** | `core.emit` / `emitFast` / `callCapability` / `getService` | ops/s、单次开销、监听器扇出成本 | 记录 + 回归比对 |
| **L2 工具路径** | `danger-patterns` → `destructive-gate` → `tool-executor` | µs/call、ReDoS 最坏耗时、**误判/漏判率** | **硬门禁** |
| **L3 上下文/会话** | `trimMessages`、`saveHistory`、`loadSession` | ms @ 消息数 N、内存、追加写摊还成本 | **硬门禁** |
| **L4 网关** | `/health`、`/ready`、`/v1/*`、连接上限 | req/s、p95/p99、错误率、fd/listener 泄漏 | **硬门禁** |
| **L5 端到端** | 真实免费模型（LongCat 免费档） | **我们的开销** = e2e − 上游直连 | 仅记录 |

**L2 是本方案的重心**。理由：安全判据跑在**每一次工具调用**的必经路径上，它是唯一「既有延迟成本、又有正确性成本」的模块。性能优化如果以漏判为代价，那是负收益 —— 所以 L2 的指标必须**同时**报延迟和准确率，两个数字放在同一张表里看。

---

## 3. 指标定义（避免"各说各话"）

| 指标 | 定义 | 采样方式 |
|---|---|---|
| `p50/p95/p99` | 最近秩（nearest-rank），对单次操作耗时排序后取 | 每场景 ≥ 2000 次 |
| 吞吐 | 完成操作数 / 墙钟秒 | 固定并发，固定总请求数 |
| `ns/op` | 单次操作纳秒 | 预热 ≥ 2000 次后测 |
| RSS | `process.memoryUsage().rss` | 稳定期采样，非瞬时 |
| `t_ready` | `spawn` 到 `/ready` 返回 200 的墙钟 | 每场景 5 次取分位 |
| ReDoS 最坏耗时 | 单条正则对对抗输入的单次耗时上界 | 超时即判失败（不等待） |
| 漏判率 | 危险语料中被放行的比例 | 必须 **0** |
| 误判率 | 良性语料中被拦截的比例 | 必须 **0** |

**预热纪律**：所有 `ns/op` 类指标先跑 2000 次丢弃。JIT 未预热时的数字通常高一个数量级，混进结果会得出"优化 10 倍"的假结论。

**GC 纪律**：内存相关场景用 `--expose-gc`，每个采样点前手动 `gc()`。不带这个参数测出来的 RSS 含未回收垃圾，噪声大于信号。

## 4. 场景矩阵

编号规则：`层-序号`。`H` = 硬门禁（不达标即失败），`R` = 记录（存基线，供下轮比对）。

### L0 冷启动

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L0-01 | 最小装配启动 | `--scene base-system` | `t_ready` p50/p95 | R |
| L0-02 | 对话场景 | `--scene chat` | `t_ready`、RSS | R |
| L0-03 | 编码场景 | `--scene coding`（含全部工具） | `t_ready`、RSS | R |
| L0-04 | 网关场景 | `--scene gateway-lite` | `t_ready`、RSS | R |
| L0-05 | 冷启动稳定性 | 同场景连续 5 次 | 极差 / p50 | R（> 3× 需解释） |

### L1 内核原语

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L1-01 | `emit` 无监听器 | 1e6 次 | ns/op | R |
| L1-02 | `emit` 10 监听器扇出 | 1e6 次 | ns/op | R |
| L1-03 | `emitFast` vs `emit` | 1e6 次 | 比值 | R（`emitFast` 应 ≤ `emit`） |
| L1-04 | `callCapability` 热路径 | 1e5 次 | ns/op | R |
| L1-05 | `getService` 命中 | 1e6 次 | ns/op | R |
| L1-06 | 监听器注册/注销 1e4 轮 | —— | 是否泄漏 | **H**（注销后计数归零） |

`emit` 会做 `Object.freeze({...payload})` 加 `toISOString()`（见 `src/core/core.js:183`），这是**有意**的：事件不可变 + 时间戳统一。L1-03 存在的意义就是量化这笔开销，而不是把它"优化"掉。如果将来要动，必须先有这组数字。

### L2 工具路径（重心）

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L2-01 | 危险判定：良性命令 | 200 条 × 500 次 | µs/call | R |
| L2-02 | 危险判定：危险命令 | 300 条 × 500 次 | µs/call | R |
| L2-03 | **对抗输入（ReDoS）** | 10 组形态 × 5k/60k 两档 | **放大比** | **H**（≤ 20×，线性≈12） |
| L2-04 | 软闸 `check()` 良性路径 | 1e4 次 | µs/call | R |
| L2-05 | 软闸计数：大目录 | 10k 文件目录 | ms/call、是否超时 | R |
| L2-06 | 工具执行全链路（只读） | 2e3 次 | µs/call | R |
| L2-07 | **安全语料零漏判** | 300 条危险命令 | 漏判数 | **H**（= 0） |
| L2-08 | **良性语料零误判** | 200 条正常命令 | 误判数 | **H**（= 0） |
| L2-09 | 判定结果在高负载下不变 | 1e5 次混合后复测 L2-07/08 | 差异 | **H**（= 0） |
| L2-10 | 并发判定隔离 | 8 并发 × 各自会话 | 状态串扰 | **H**（= 0） |

L2-09/L2-10 是这套压测**真正的价值**所在。判据里藏状态（`_pending`、`_readFiles`、attempts 计数）时，正确性 bug 只在并发和长时间运行下暴露 —— 单测跑 15 条用例永远是绿的。

### L3 上下文与会话

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L3-01 | `trimMessages` 滑动窗口 | 100 / 1k / 5k / 10k 消息 | ms、保留条数 | **H**（10k < 200ms） |
| L3-02 | 超预算退化路径 | 消息体 > 窗口 | 是否返回最小集 | **H**（不抛异常） |
| L3-03 | 巨型单条消息 | 1 条 1MB | ms、是否 OOM | **H**（不崩） |
| L3-04 | 会话追加写 | 1 次 load + 1000 次 save | 总 ms、文件可解析 | **H**（< 5s） |
| L3-05 | 会话读取 | 10k 条历史 | ms | R |
| L3-06 | 多会话并行写 | 32 会话 × 100 次 | 错误数、串话 | **H**（= 0） |

### L4 网关

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L4-01 | `/health` 吞吐 | 并发 1 / 8 / 32 / 128 | req/s、p95/p99 | R |
| L4-02 | 并发上限 | 500 并发连接 | 错误数、崩溃 | **H**（0 崩溃） |
| L4-03 | 保持连接复用 | 64 并发 × 2000 请求 | 错误率、fd 数 | **H**（0 错误） |
| L4-04 | 超限请求体 | 大 body | 413 而非挂死 | **H** |
| L4-05 | 跨域拒绝路径 | 伪造 Origin | 403 且不泄漏 | **H** |
| L4-06 | 长时间低负载 | 5 分钟 steady | RSS、fd 漂移 | **H**（< 20%） |

### L5 端到端（真实免费模型，仅记录）

| ID | 场景 | 负载 | 指标 | 判据 |
|---|---|---|---|---|
| L5-01 | 单轮问答 | 5 次串行 | e2e、上游直连、**差值** | R |
| L5-02 | 单次工具调用闭环 | 3 次 | 全链路 ms | R |
| L5-03 | 3 并发会话 | 3 × 1 轮 | 成功率、p95 | R |

> L5 的并发**不得超过 3**。免费档额度有限，压它只会得到 429 —— 那测的是厂商限流，不是土行孙。任何 L5 数字都必须与"上游直连"同时给出，否则无法归因。

## 5. 判据总表

**硬门禁（H）** —— 硬件无关，任何机器都必须过：

1. L2-03 ReDoS：**放大比 ≤ 20×**（同一形态 5k → 60k 的耗时比；线性≈12，二次≈144），
   外加绝对上限 50ms/单次（防挂死）。只测绝对值是错的 —— 慢机器上的线性也慢，会误判成退化。
2. L2-07 危险语料漏判 = 0
3. L2-08 良性语料误判 = 0
4. L2-09 高负载后判定结果不变
5. L2-10 并发判定零串扰
6. L1-06 监听器注销后计数归零
7. L3-01/02/03 不抛异常、不 OOM、10k 消息 < 200ms
8. L3-04/06 会话写入可解析、零串话
9. L4-02/03/04/05 零崩溃、零错误、超限有明确响应
10. L4-06 RSS 漂移 < 20%

**记录型（R）** —— 存基线，用于**回归比对**，不单独判成败：

- 上轮基线的 **2 倍**以上视为回归，需在报告里写明原因；否则视为噪声。
- 首次运行无基线时，只记录，不比较。

这个分法是有意的：把「机器快慢」从「代码好坏」里剥出来。否则 CI 机器降频会让门禁变红，最后所有人都学会无视红 —— 门禁一旦被人习惯性忽略，等于没有。

## 6. 执行方式

```bash
# 全量（约 6 分钟；含 10 分钟 soak 时改用 --soak）
npm run test:stress

# 快速（跳过 soak 与大目录场景）
npm run test:stress -- --quick

# 只跑某层
npm run test:stress -- --only=L2

# 含真实免费模型（读仓库根 .env，需 TUSUNSUN_* 已配）
npm run test:stress -- --only=L5 --live
```

**环境要求**

- Node ≥ 18（与 `engines` 一致），L0–L4 需要**无外网**也能跑通
- 单机、无其他重负载任务；报告必须写明 CPU 核数与内存
- L5 需要 `TUSUNSUN_API_KEY`；缺失时该层 **`[NOT_RUN]` 且非零退出**，不得静默跳过算通过

**时长参考**（本机实测）：L0 ≈ 5s · L1 ≈ 0.3s · L2 ≈ 3s · L3 ≈ 0.3s · L4 ≈ 35s · L5 ≈ 5s · G ≈ 120s。
全量约 3 分钟；`--soak` 把 G 拉到 600s。

**可复现性约定**

- 每个 `ns/op` 场景固定迭代数，不用"跑满 N 秒"（那会让慢机器跑更少次数，数字不可比）
- 报告落 `test-results/stress/report.json` + `report.md`（已被 `.gitignore` 忽略，不入库）
- 报告头固定写入：commit、Node 版本、CPU 型号/核数、内存、内核行数

---

## 7. 报告格式

人读（markdown 表）+ 机读（JSON）双份，同一份数据渲染两次，避免手抄。

```
## 环境
commit 558ba15 · node v22.22.2 · 12 vCPU · 15 GiB · 核心 2079 行

## 结果
| ID | 场景 | 指标 | 数值 | 判据 | 结论 |
| L2-03 | ReDoS | 最坏单次 | 0.31 ms | < 5 ms | PASS |
...
## 失败项
（逐条给复现命令与最小输入）
```

失败项必须带**最小可复现输入**。只写"L2-03 失败"是没用的报告 —— 下一个接手的人得从零重找一遍。

## 7.5 结果登记

每轮结论在两处留痕：

- `test-results/stress/report.md` + `*.json`（机器产物，已被 `.gitignore` 忽略）；
- `docs/quality/stress-baseline-<日期>.md`（人读快照，入库）—— 带**硬件指纹**，
  下轮比对时先看两台机器是不是同一档，不同档的数字没有可比性。

## 8. 已知限制（必须随报告一起给出）

1. **文本判据不是安全边界**。`Y024` 是"拦住显然的手滑"，不是"防住蓄意的攻击"。写进文件、下一次调用再执行的内容，文本判据看不见（详见 `plugins/_lib/danger-patterns.js` 注释与 CHANGELOG v0.9.14）。压测不改变这一点，R1 的进程级沙箱才改变。
2. **单机压测不含网络**。L4 的数字是 loopback 上限，真实部署要打折。
3. **L5 不可作容量依据**。免费档限流决定了它的天花板，与土行孙无关。
4. **未覆盖**：多租户隔离、磁盘 IO 饱和、Windows 平台、长时（>1h）稳定性。
5. **GC 抖动**：即使 `--expose-gc`，V8 的分代回收仍会带来个位数百分比噪声。所以记录型判据用 2× 阈值，不用 5%。

## 9. 资产分发口径

`test/stress/` **不进发布包**（靠 `package.json` 的 `files` 白名单显式不列它 —— 注意
`files` 里一旦写了裸 `test/`，整目录都会被带进去，`.npmignore` 管不住）。原因沿用 R0-113 的决定：

- 压测阈值与机器强相关，随包分发会让用户在慢机器上得到"红"，那是误报；
- 「跑过压测、全绿」这句话必须只能由真实资产产生 —— `test/run-stress.mjs` 在资产缺失时**非零退出**，不伪装通过。

因此压测证据只从开发树产出，报告随发布说明附上关键结论与硬件信息。
